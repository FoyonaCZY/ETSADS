# ETSADS：欧洲卡车模拟 2 自动驾驶系统设计

> 版本 0.3.1（新增车内/车外视角支持；主语言改为 Rust，不使用 Python）· 步骤级实现计划见 [IMPLEMENTATION.md](IMPLEMENTATION.md) · 目标平台 Windows 11 + ETS2（单机模式）
>
> 本机已知硬件：RTX 5060 Ti 8GB（Blackwell，需 CUDA 12.8+、TensorRT 10.x）

---

## 0. 目标：什么叫"上限高"

能力分级（每一级都是下一级的子集，架构从第一天就按 L5 设计，避免中途推倒重来）：

| 级别 | 能力 | 标志性难点 |
|---|---|---|
| L1 | 车道保持 + 自适应巡航 | 横纵向控制、跟车 |
| L2 | 高速领航：变道、汇入、驶出、收费站 | 交互式变道、匝道汇入 |
| L3 | 全路网：城市路口、红绿灯、环岛、让行、掉头 | 挂车内轮差、无保护左转 |
| L4 | 门到门：到公司场站并倒车入位 | 牵引车+挂车倒车规划（不稳定系统） |
| L5 | 全职业自动化：接单、加油、休息、轮渡/火车、夜间雨天 | UI 自动化、长时任务规划 |

衡量指标（全部自动统计，见 §12）：每次接管平均里程（km/接管）、每百公里违章（碰撞、闯红灯、超速、逆行，以游戏自身罚单事件为准）、舒适度（加加速度、横向加速度）、路线完成率、交付成功率、平均车速与人类基线之比。

## 1. 决定上限的六条原则

1. **能拿真值就拿真值。** 这里是游戏，不是现实世界。自车位姿、车道级地图、周围车辆、红绿灯状态，都能直接从游戏拿到精确值。现实自动驾驶最难的定位和感知，在这里大部分可以绕开。视觉负责冗余和兜底，不当唯一信息源。
2. **真值同时是训练数据。** 同一份特权信息既用来直接驾驶，也用来给画面自动标注（"learning by cheating" 思路）。标注数据因此不受数量限制，以后训练出的视觉模型在游戏更新、内存读取失效时还能接替。
3. **接口先行，模块可换。** 感知 → 世界模型 → 规划 → 控制之间用固定的消息契约连接。规则模块、学习模块、端到端模型都在同一接口下替换，控制和安全层不用改。
4. **数据飞轮加离线闭环仿真。** 每次运行都全量录制，可回放、可回归测试，也能离线以远超实时的速度训练和评估规划器。决定长期上限的主要是这一条。
5. **按卡车专门建模。** 铰接车辆运动学（牵引车+挂车）、扫掠包络、长制动距离、载重变化、坡道。拿小车算法套在卡车上，上限很早就会碰顶。
6. **安全监督独立于主栈。** 用独立进程、最简单的代码、独立的数据通路。主栈怎么改，安全兜底都在。

## 3. L0 游戏接口层

### 3.1 数据通道

| 通道 | 来源 | 内容 | 稳定性 |
|---|---|---|---|
| 遥测 | SCS 官方 Telemetry SDK（当前 1.14） | 自车世界位姿（double 精度）、线/角速度、加速度、转速、挡位、方向盘（用户输入 `truck.input.*` 与实际生效 `truck.effective.*` 分开给）、限速 `truck.navigation.speed.limit`、到终点距离/时间、车轮转角、刹车温度、挂车位姿、车辆配置（轮位、挂点）、任务信息（货重、目的地城市/公司）、游戏事件（罚单类型、交付、收费站、轮渡） | 官方接口，跨版本稳定 |
| 输入 | SCS 官方 Input SDK（语义输入设备） | 连续轴：转向、油门、刹车、离合；按键：转向灯、灯光、雨刷、喇叭、挡位、交互键、菜单 | 官方接口，稳定 |
| 扩展状态 | 社区插件（逆向读内存） | 最近 40 辆交通车（含最多 3 节挂车）、最近 40 辆停放车、最近 40 个信号灯/闸门及其状态、当前导航路线（节点 ID 序列）、相机 FOV/位置/朝向/投影矩阵 | 依赖逆向，游戏更新可能失效 |
| 画面 | 进程内 D3D11 `Present` Hook | 游戏渲染出的每一帧，零拷贝共享内存环形缓冲 | 依赖 DX11 渲染器 |

### 3.2 起步方案：自研遥测/输入 + 复用 ETS2LA 的两个 DLL

[ETS2LA](https://github.com/ETS2LA) 已经把游戏侧插件拆成独立仓库。最难的逆向部分直接复用，官方 SDK 能做的部分自己写：

- **遥测和输入：自研 Rust DLL**（§3.3 的 `etsads_bridge`，从第一天就写）。官方 SDK 接口小，自己写也不费事。ETS2LA 的 `controller` 和 `telemetry` 不用：功能和自研重复，而且 `controller` 是 GPL-3.0。
- **扩展状态：复用 `ETS2LA/plugin`（MIT）。** 共享内存 `Local\ETS2LATraffic`、`Local\ETS2LASemaphore`、`Local\ETS2LARoute`、`Local\ETS2LACameraProps` 等，README 写明了每块的结构格式，Rust 直接按格式读取。信号灯状态枚举：OFF=0、ORANGE_TO_RED=1、RED=2、ORANGE_TO_GREEN=4、GREEN=8、SLEEP=32；闸门：CLOSING=0、CLOSED=1、OPENING=2、OPEN=3。它靠读游戏内存工作，游戏更新后由上游跟进偏移。
- **画面：起步复用 `ETS2LA/capture`（GPL-3.0）。** 它 Hook DX11 `Present`，用 6 帧环形共享内存发布画面。README 没写共享内存布局，要从它的 C++ `FrameReader` 源码读出来，在 Rust 里重新实现读取端。后期换成自研方案（§3.3）。

**许可证**：起步阶段 `capture` 是 GPL-3.0，自用不受影响；P1 末尾换成自研 `etsads_gfx.dll`。地图导出器依赖的 TruckLib 是 GPL v2，所以导出器作为独立程序随之受 GPL v2 约束；它导出的数据文件和主项目不受影响。

### 3.3 终态方案：自研统一桥接插件 `etsads_bridge.dll`（Rust `cdylib`）

起步时只有遥测和输入。P1 末尾再加一个独立的 `etsads_gfx.dll`，用同一个 `Present` Hook 依次完成截图和 Dear ImGui 叠加绘制，保证"先截图、后画叠加层"（见 IMPLEMENTATION §4.9）。扩展状态继续用上游的 MIT 插件；如果上游停止维护，MIT 许可也允许移植成 Rust。合并后换来三点：

- **帧对齐**：遥测、扩展状态、画面帧共用同一个 `frame_id` 和 `sim_time`，融合时没有时间错位。
- **更短的看门狗**：输入命令过期阈值设为 200 ms（ETS2LA 的 controller 是 3 秒）。超时先松油门、轻刹，再释放。
- **单一版本校验点**：插件启动时检查游戏版本和结构体布局，不匹配就拒绝输出扩展状态，系统自动降级为纯视觉模式。

共享内存协议：固定头部 `{magic, schema_version, struct_size, game_version, seq}` + seqlock（写端奇偶序号，读端校验重读）+ 环形缓冲。所有消息携带 `frame_id / sim_time_us`。

DLL 运行在游戏进程里，有两条硬规矩：
- 所有 FFI 入口用 `catch_unwind` 包住，panic 绝不能跨进游戏，否则游戏直接崩溃。
- DLL 里只做采集和转发，不做重计算，不能拖慢游戏帧。

### 3.4 游戏设置清单（保证可控、可复现）

- 渲染器选 DX11；无边框窗口、固定分辨率（1920×1080）；帧率锁 60。
- 自动挡；关闭转向辅助类选项；控制器设置里转向非线性设为 0、死区设为 0。实际的"轴值→车轮转角"映射靠系统辨识测量（§9.3），不假设线性。
- 视角不做限制：车内、车外都支持，驾驶中可以随时切换或用鼠标转视角（见 §6.7）。建议关闭头部物理，减少车内画面抖动，但不是必须。
- 打开开发者控制台（`config.cfg`：`uset g_developer "1"`、`uset g_console "1"`），用于场景控制，见 §12.4。
- **锁定游戏版本**：Steam 属性 → 测试版里可以选历史版本。游戏更新后，先在旧版本上继续开发，等扩展插件适配新版再升级。
- 只在单机模式使用，不要在 TruckersMP 等联机环境运行。

## 4. 坐标系与时间

- **世界坐标**：SCS 坐标系 X 朝东、Y 朝上、Z 朝南，单位米。heading 为 `[0,1)` 的归一化值，0=北，逆时针增加（0.25=西）。内部统一换算到右手 ENU（x 东、y 北、z 上，yaw 为弧度）。转换函数只写一处，配齐单元测试。约定以 SDK 头文件 `scssdk_value.h` 的注释为准。
- **大坐标精度**：世界坐标数值可达数十万米。存储用 double，计算时减去局部原点（按 sector 或每 1 km 重置），float32 只用于局部坐标。
- **时间**：所有模块只认 SDK 的模拟时间戳 `sim_time_us`，不用系统时钟。游戏暂停或进入菜单时时间冻结，控制器检测到后释放输入。
- **对齐**：SDK 的遥测"帧"是固定步长的物理步，不是渲染帧；输入在每个渲染帧开始时处理，渲染画面是两个物理步之间的插值。控制回路由物理步驱动，实际延迟在 P0 实测（IMPLEMENTATION §1 的 E1、E9）。

## 5. L1 HD 地图（离线导出 + 在线查询）

### 5.1 导出

游戏文件里有完整的车道级信息，相当于自带一张高精地图：

- **道路**（road item）：引用 road look 定义，包含左右车道数、车道宽度、偏移、中央分隔，可以沿节点样条生成每条车道的中心线和边界。
- **预制件**（prefab，`.ppd`，即路口、环岛、收费站、公司场站）：内含 **AI 导航曲线**（路口内每条可行车道的轨迹及其连接关系、通行规则标志）、**信号灯位置**、**停车位/挂车位**（交付泊车目标）、触发点。
- 限速标志、收费站、边检、轮渡/火车站点。

工具链：用 [TruckLib](https://github.com/sk-zk/TruckLib)（C#）写一个小型导出器 `tools/map_export`（.NET），直接读取当前版本游戏 + DLC + 已启用 mod 的 `.scs` 归档。ETS2LA 的 C# 重写版也走这条路。prefab 转道路多边形的逻辑可以参考 [truckermudgeon/maps](https://github.com/truckermudgeon/maps) 的 parser 和 prefabs-app。

导出产物（Parquet 表，缓存键 = 游戏版本 + DLC 列表 + mod 列表哈希）：

| 表 | 关键字段 |
|---|---|
| `lanes` | id, 中心线折线 (x,y,z), 宽度, 限速, 车道类型, 所属 road/prefab, 前驱/后继, 左右邻道 + 是否允许变道 |
| `conflicts` | 路口内互相交叉的导航曲线对、冲突点位置、优先级关系 |
| `stop_lines` | 位置, 关联信号灯 ID 或让行规则 |
| `signals` | 信号灯 ID, 世界位置, 控制的车道集合 |
| `drivable_polygons` | 路面多边形（用于挂车扫掠校验） |
| `slots` | 公司场站停车位 / 挂车位 位姿 |
| `pois` | 收费站、边检、加油站、休息区、轮渡/火车 |

### 5.2 在线查询与地图匹配

- 按 sector 分块懒加载自车周围 2 km，用 `rstar`（R*-树）建空间索引。
- **地图匹配**：遥测位姿本身是精确值，难点只在车道归属。重叠路段（立交、并行匝道）用"距离 + 航向 + 拓扑连续性"做 HMM 匹配。高度 z 用来区分立交上下层。
- **自检**：用相机投影矩阵把车道线投影到实时画面上叠加显示，第一天就能看出地图对得准不准。

## 6. L2 感知

### 6.1 定位

直接用遥测，不需要感知。

### 6.2 动态目标：特权 + 视觉双源

- **源 A（特权）**：扩展状态里的交通车位姿/速度/挂车，精确、无遮挡问题，覆盖最近 40 辆，作为主源。
- **源 B（视觉）**：2D 检测（优先选 Apache-2.0 许可的 RT-DETR / D-FINE / RF-DETR 系列；Ultralytics YOLO 是 AGPL，注意许可）+ 单目 3D：利用已知投影矩阵和地图地面高度，把检测框底边反投影到地面得到 BEV 位置；后续可升级为用自动标注训练的 BEV 模型。
- **融合**：特权源存在时以它为准，视觉用来交叉校验。两源持续不一致（例如游戏更新导致内存布局错位）时，告警并切换到视觉主导。

### 6.3 信号灯

地图给出信号灯位置和它控制的车道，扩展状态给出实时状态，两者直接关联即可。视觉兜底只需要把已知位置投影到画面上裁出小图做分类，比全图检测稳定得多。

### 6.4 地图里没有的东西

新版游戏有随机道路事件（事故、施工封道）和临时障碍，地图里不会出现。所以需要视觉可行驶区域分割，作为规划的额外约束。这是纯地图方案的盲区，也是视觉栈必须存在的直接理由。

### 6.5 自动标注流水线（数据飞轮核心）

```
录制帧 + 同帧特权状态 + 投影矩阵
   ├─► 交通车 3D 框 → 投影 → 2D/3D 检测标签（按深度做遮挡剔除）
   ├─► 地图车道线 → 投影 → 车道线/可行驶区域标签
   └─► 信号灯位置+状态 → 投影 → 信号灯 ROI + 状态标签
配合控制台切换天气/时间/交通密度 → 低成本获得多样性数据
```

### 6.6 GPU 预算（8GB 显存与游戏共享）

游戏 1080p 中画质约占 4–5 GB，推理总预算控制在 ≤ 2 GB。全部模型用 TensorRT FP16（检测模型可用 INT8），输入分辨率 960×540 级别，单帧推理 ≤ 8 ms。以后上大模型时，考虑第二块 GPU，或者把推理放到另一台机器、经局域网传帧。

### 6.7 视角支持：车内 / 车外

**原则：驾驶主回路与视角无关。** 遥测、扩展状态、地图都是世界坐标数据。玩家用什么视角、中途怎么切换、用鼠标怎么转，都不影响驾驶。只有三类功能依赖画面，需要按视角处理：视觉感知、自动标注、游戏内叠加显示。

**相机状态（每帧）**

- 从扩展状态 `Local\ETS2LACameraProps` 读取 FOV、相机位置与旋转、投影矩阵，以及渲染用的插值车辆位姿，组成 `CameraState`（§14）。
- 视角分类：把相机位置变换到驾驶室坐标系。落在驾驶室包围盒内为 `interior`，在车后上方为 `chase`，其余（俯视、保险杠、车轮、电视镜头、自由相机）为 `other`。
- 切换检测：相机相对车辆的位姿突变即判为切换。此时视觉跟踪重置，之后若干帧的视觉输出标记为无效。
- 所有"图像 ↔ 世界"换算一律使用当帧相机矩阵，代码里不允许写死标定参数。投影时用**渲染插值位姿**，不用遥测的物理位姿。两者有细微差别，用错了叠加层会抖。

**两种视角的差异**

| | 车内视角 | 车外视角（追尾） |
|---|---|---|
| 前方 | 好，接近驾驶员视线 | 被自己的挂车大面积遮挡，只能看到挂车上方和两侧远处 |
| 侧后方 | 只有后视镜 | 好，两侧车道和挂车位置都看得到 |
| 自车遮挡 | 仪表台、A 柱、方向盘、雨刷，相对相机基本静止 | 牵引车和挂车，随铰接角和镜头环绕变化 |
| 相机运动 | 头部物理会抖 | 跟随有延迟，玩家可以环绕、缩放 |
| 擅长 | 前向感知、红绿灯、车道线 | 变道盲区、倒车入位、观察挂车 |

**遮挡掩码**

- 车内：内饰相对相机静止，行驶时画面中方差很低的区域就是内饰。按"车型 + 座椅位置"自动计算并缓存，不用手工画。屏幕上的 HUD（导航、仪表 UI）用同样方法得到。
- 车外：用遥测的牵引车、挂车位姿和尺寸投影出自车包围盒，作为动态掩码；再训练一个"自车"分割类别细化边缘，标签同样来自投影。

**后视镜当作现成的后向相机。** 车内的实体后视镜和车外的 HUD 后视镜都实时渲染后方画面。镜面几何复杂，不做 3D 重建，只在后视镜区域做 2D 分类："盲区里有没有车"。标签直接取自特权数据（盲区范围内是否有交通车），不需要知道镜面几何。

**模型训练**

- 自动标注天然支持任意视角：每帧用当帧投影矩阵投影真值即可。
- 感知模型把相机内外参作为输入（LSS / BEVDet 一类，显式用相机矩阵把图像特征提升到 BEV），一个模型同时覆盖车内和车外，不按视角分别训练。
- 采集数据时有意覆盖：两种视角、不同环绕角度和缩放、不同车型和座椅位置。采集脚本通过输入插件的相机按键自动切换视角。

**视觉能力随视角分级。** 在视觉为主的降级模式下（特权数据失效），安全监督按当前视角限制能力：

- `interior`：前向视觉完整，允许高速 L2。变道前须由后视镜盲区检测确认。
- `chase`：前向被挂车遮挡，降低限速、加大跟车距离，并提示玩家切回车内视角（开启自动视角策略时自动切换）。
- `other`：关闭视觉，只执行最小风险策略。

**游戏内叠加显示（AR 调试）。** 用当帧相机矩阵把规划轨迹、车道线、目标框、信号灯状态投影后画到游戏画面上，车内车外都能对准。实现方式：在帧捕获插件已经 Hook 的 `Present` 里用 Dear ImGui 绘制。这样与游戏帧同步，没有延迟，独占全屏也能显示。**顺序必须是先把帧拷贝给视觉，再画叠加层**，否则模型会看到自己画上去的东西。

**自动视角策略（可选，默认关闭，尊重玩家的选择）。** 倒车入位时切到俯视或车外视角，完成后切回；视觉降级模式下切回车内视角。

## 7. L3 世界模型（Scene）

每个规划周期生成一份不可变的 `Scene` 快照，供预测和规划使用：

- 自车：位姿、速度、加速度、转向、挡位、总质量、每节挂车位姿与**铰接角**（牵引车航向 − 挂车航向）。
- 局部车道图：自车周围的车道、连接、冲突区、停止线（向量化折线表示）。
- 目标：融合跟踪后的车辆，带车道归属、速度、加速度、尺寸、挂车、来源与置信度。
- 交通控制：相关信号灯状态与剩余距离、让行关系、收费站/闸门状态。
- 路线：车道级路线 + 下一个必须的变道/转向点距离。
- 环境：天气、昼夜、路面湿滑等，影响跟车距离和制动预期。

表示方式采用向量化折线 + 属性（VectorNet / PlanTF 风格），规则规划器和学习型规划器读同一份数据。

## 8. L4 预测

- **v1**：沿车道图的常速/IDM 外推，在分叉处生成多假设（按转向灯和速度变化赋权）。ETS2 的 AI 交通是规则驱动的，可预测性很高，v1 已经能用。
- **v2**：特权交通数据天然是海量带标签轨迹，可以直接训练学习型预测（QCNet / MTR 风格的小模型），重点学 AI 车加塞、路口抢行这类边界行为。
- 输出多模态轨迹 + 概率，供规划做风险加权的碰撞检测。

## 9. L5 规划

### 9.1 任务与路线

- 目的地：遥测给出任务目的地城市和公司，在地图里找到对应公司 prefab 和交付车位。
- 车道级 A*：代价包括时间、收费、变道次数，以及转弯对卡车的难度（急弯、窄路惩罚）。
- 与游戏 GPS 对齐：扩展状态里的路线节点 ID 可以映射到地图节点。默认跟随游戏路线，游戏的距离和时间提示、限速信息才能保持一致；自有路由用于车道级细化和离线规划。

### 9.2 行为层（场景化状态机）

每个场景是独立模块，有明确的进入/退出条件和自己的参数，可以单独测试、单独替换（Apollo 的 scenario 思路）：

`车道保持 / 跟车` · `主动变道`（路线需要、超慢车） · `匝道汇入 / 驶出` · `信号灯路口` · `让行路口 / 无保护左转` · `环岛` · `收费站 / 边检`（停在停止位，触发交互键，等闸门 OPEN） · `加油 / 休息` · `场站泊车 / 倒车入位` · `最小风险策略`（打双闪、车道内减速停车）

### 9.3 运动规划（三层，上限逐级提升）

1. **基线：Frenet 采样 + ST 速度规划。** 参考线取路线车道中心线，横向偏移 × 目标速度 × 时域采样，代价项为舒适度、进度、偏离、风险。速度单独在 ST 图上做 DP + QP。碰撞检测用**牵引车 + 挂车的扫掠包络**对预测轨迹做检查。
2. **优化：时空轨迹优化。** 自写 iLQR，约束多时改用 OpEn（纯 Rust 的非线性 MPC 求解器），在牵引车-挂车运动学模型下对基线轨迹精修。约束：挂车包络始终在 `drivable_polygons` 内、铰接角上限（防折叠）、转向角和角速度上限。
   - 关键点：路口导航曲线是给各种车辆用的。如果让牵引车前轴沿曲线走，挂车会啃路缘。正确做法是把**挂车轴的轨迹**也纳入约束，自动算出"外摆入弯"的走线。
3. **低速非结构化：泊车与倒车。** Hybrid A*（牵引车-挂车模型，含折叠约束，配解析扩展），再用倒车 MPC 跟踪。倒车时挂车是开环不稳定系统，必须对铰接角做闭环反馈。场站车位位姿直接取自地图 `slots`。

运动学模型（单挂车，挂点在后轴后方 M 处；L1 为牵引车轴距，L2 为挂点到挂车轴距离，均从遥测车辆配置中的轮位和挂点计算）：

```
ẋ  = v·cos θ1        ẏ = v·sin θ1        θ̇1 = v·tan δ / L1
θ̇2 = v·sin(θ1−θ2)/L2 − v·M·cos(θ1−θ2)·tan δ /(L1·L2)
```

多轴挂车取等效轴距，用实测数据拟合修正。

4. **上限路线：学习型规划器。** 在向量化 Scene 上训练 Transformer / Diffusion 规划器（参考 PlanTF、Diffusion Planner），数据来自人类驾驶录制和规则规划器日志。部署形态是"学习模型出候选轨迹，规则层校验并否决"：学习模型负责拟人和处理复杂交互，规则层守底线。之后在离线闭环仿真里用 RL 微调（§12.3）。最终可以把整套特权专家蒸馏成"画面 → 轨迹"的端到端模型，输出接口仍是 `Trajectory`，控制和安全层不用改。

## 10. L6 控制

- **输出**：转向轴 [-1,1]、油门 [0,1]、刹车 [0,1]，外加缓速器/发动机制动档位和各类按键。
- **频率**：每游戏帧一次，只依赖遥测和最新轨迹，不等视觉。
- **横向**：起步用 Pure Pursuit / Stanley 加曲率前馈；终态用 LTV-MPC（含挂车状态），带转向角速度限制和执行延迟补偿（把状态按测得的延迟前推）。
- **纵向**：规划给目标加速度，逆模型 `f(v, 挡位, 总质量, 坡度, a_cmd) → 油门/刹车`，用录制数据拟合（查表或小 MLP）。质量（货重）和坡度（俯仰角）做前馈，PI 修正残差。长下坡优先用缓速器和发动机制动，同时监控刹车温度。
- **系统辨识**：在空旷场地自动执行标准动作（不同车速下的转向阶跃、油门/刹车阶跃、滑行），拟合转向映射、执行延迟、加减速特性，按"车型 + 挂车配置"缓存参数。换车后先自动标定，再上路。

---

## 11. L7 安全监督（独立进程）

- **看门狗**：每个上游模块的心跳和数据新鲜度。任何一路过期，进入最小风险策略。
- **命令校验**：限幅、变化率限制、NaN 检查。
- **独立 AEB**：直接读取原始特权交通数据（不经过融合和规划），按 TTC 和所需减速度触发紧急制动；同时设置视觉通路的独立 AEB。
- **硬约束**：速度不超过限速上限；按地图检查是否越出车道或行驶区域。
- **人工接管**：遥测中的用户转向、踏板输入超过阈值，或按下热键，立即交还控制。暂停或进入菜单时释放全部输入。
- **事件记录**：每次介入都打标记写入录制，供后续挖掘场景。

## 12. 工具链与数据飞轮

### 12.1 语言与运行时框架

**语言分工**

| 语言 | 用在哪里 |
|---|---|
| **Rust** | 主语言。驾驶栈、安全监督、录制、仿真、自动标注、模型训练，以及自研游戏侧 DLL（`cdylib`） |
| C++ | 自己不写。只以二进制形式复用上游 ETS2LA 的扩展状态插件，起步阶段还有帧捕获插件 |
| C# | 只用于离线地图导出工具：TruckLib 是目前能可靠读取当前版本地图的库。导出结果是 Parquet 文件，运行时不依赖 .NET |
| Python | 不用 |

**进程划分**

- 驾驶栈是一个多线程进程：感知、世界模型、预测、规划、控制各占线程，线程间用通道传 `Arc` 快照（天然只读），省掉进程间序列化和延迟。
- 安全监督和录制器是独立进程，经 iceoryx2 订阅数据（Rust 原生，零拷贝共享内存，支持 Windows），图像只传共享内存句柄。跨进程消息用 `#[repr(C)]` 定长结构。
- 消息契约集中在 `crates/msgs`，带统一头部 `{sim_time_us, frame_id, seq, source}`。

**主要依赖**

| 用途 | crate |
|---|---|
| Windows API、共享内存 | `windows` |
| SCS SDK 绑定 | 用 `bindgen` 从官方头文件生成（社区的 `scs-sdk` crate 还在 0.1 版，可参考） |
| DX11 Hook、游戏内叠加 | `hudhook`（`Present` Hook + Dear ImGui） |
| 3D 变换与投影、优化里的矩阵 | `glam`、`nalgebra` |
| 几何、空间索引 | `geo`、`rstar` |
| 优化求解 | 自写 iLQR；`clarabel`（QP/锥规划，用于 ST 速度规划、LTV-MPC）；`optimization_engine`（OpEn，非线性 MPC） |
| 推理 | `ort`（ONNX Runtime，TensorRT / CUDA 执行器） |
| 训练 | `burn`（CUDA 后端） |
| 进程间通信 | `iceoryx2` |
| 录制、可视化 | `mcap`、`rerun`；视频交给 ffmpeg 的 NVENC 编码 |
| 地图数据 | `parquet` / `polars` |
| 控制面板 | `egui` |

**模型训练**：P0–P4 全靠特权数据、规则和优化，不需要训练任何模型，这件事到 P5 才真正出现。默认用 `burn` 训练，保持全 Rust。它能导入 PyTorch / safetensors 格式的预训练权重，骨干网络不用从零训练。代价是论文的参考实现大多是 PyTorch，模型结构要自己移植。如果到时候某个模型移植成本太高，退路是把 Python 关在独立的离线训练目录里，只产出 ONNX 文件，运行时完全不碰 Python。

**开发环境**：VS 2022 Build Tools（C++ 工作负载）+ rustup 的 `stable-x86_64-pc-windows-msvc` 工具链；`ort`、`hudhook`、CUDA 生态都以 MSVC 为准。.NET SDK 用于地图导出。CUDA 和 TensorRT 到 P5 再装。

### 12.2 录制与可视化

- 录制器：结构化数据写 MCAP（遥测、Scene、轨迹、控制量、特权状态），画面用 NVENC H.265 编码，旁路保存 `frame_id` 对应表。
- 可视化：开发期用 [Rerun](https://rerun.io)（3D 场景、图像、时间序列同屏，支持实时和回放）；MCAP 也能直接用 Foxglove 打开。驾驶时用游戏内 AR 叠加（§6.7）直接看系统的理解和意图。
- 每次运行自动生成摘要：里程、接管点、违章、舒适度曲线。

### 12.3 离线回放仿真（决定长期上限）

- **开环回放**：用录制数据评估感知和预测，与特权真值对比打分。
- **闭环仿真**：规划器在环；自车动力学用辨识出的模型（之后可换学习型动力学模型）；其他车辆从录制轨迹出发，按 IDM 沿车道图做反应式行为（nuPlan 方法论）。可以几十到上百倍实时运行，承担规划器回归测试、超参搜索、模仿学习评估和 RL 微调。
- **场景库**：从录制中自动挖掘难例（加塞、急刹、红灯路口、环岛、接管点），作为回归测试集。每次提交都跑一遍，指标退化就拒绝合入。

### 12.4 游戏内自动化测试

开发者控制台提供场景控制：传送到指定城市、设置时间和天气、调节游戏速度（慢放调试、加速采集）、调整交通密度，再配合存档作为场景起点。具体命令名以当前版本实测为准，统一封装在 `crates/game` 的 `console` 模块里。

### 12.5 指标与裁判

把游戏本身当裁判：SDK 的游戏事件直接给出罚单（碰撞、闯红灯、超速、逆行、未开灯等）、交付结果（损伤、准时）、收费站和轮渡事件。再加上自有指标：km/接管、舒适度、与人类基线的速度比。同一路线定期让人类驾驶录制，作为基线和模仿学习数据。

## 13. 性能与延迟预算

| 环节 | 目标 |
|---|---|
| 遥测 → 控制量写回 | 同帧内 ≤ 1 ms，下一帧生效 |
| 帧捕获（进程内 Hook → 共享内存） | ≤ 2 ms |
| 视觉推理（TensorRT FP16） | ≤ 8 ms @ 30 Hz |
| 融合跟踪 | ≤ 2 ms |
| 预测 + 规划 | ≤ 30 ms @ 10–20 Hz（异步） |
| 安全监督 | ≤ 0.5 ms，每帧 |

CPU：游戏主线程负载高，自有进程用亲和性绑到其他核心，控制和安全进程提高优先级。

/// 所有消息的统一头部
#[derive(Clone, Copy, Debug)]
#[repr(C)]
pub struct Header {
    pub sim_time_us: u64,           // SDK 模拟时间，全系统唯一时钟
    pub frame_id: u64,              // 游戏帧号，跨源对齐用
    pub seq: u64,
    pub source: SourceId,
}

pub struct EgoState {
    pub header: Header,
    pub pos: DVec3,                 // ENU 世界坐标，f64
    pub yaw: f32, pub pitch: f32, pub roll: f32,
    pub vel_body: Vec3, pub acc_body: Vec3, pub yaw_rate: f32,
    pub steer_effective: f32, pub wheel_angle: f32,
    pub gear: i8, pub rpm: f32, pub mass_total: f32,
    pub trailers: ArrayVec<TrailerState, 3>,  // 位姿 + 铰接角
    pub user_input: DriverInput,              // 接管检测用
}

pub enum ViewKind { Interior, Chase, Other }

pub struct CameraState {
    pub header: Header,
    pub view: ViewKind,
    pub switched: bool,             // 本帧发生视角切换
    pub fov_deg: f32,
    pub pos: DVec3, pub rot: Quat,  // 相机世界位姿
    pub proj: Mat4,                 // 投影矩阵
    pub render_truck_pose: Pose3,   // 渲染插值位姿，投影一律用它
}

pub enum AgentSource { Game, Vision, Fused }

pub struct Agent {
    pub id: u32,
    pub source: AgentSource,
    pub pose: Pose2, pub speed: f32, pub accel: f32, pub size: Vec3,
    pub trailers: ArrayVec<OrientedBox, 3>,
    pub lane_id: Option<LaneId>,
    pub confidence: f32,
}

pub enum Direction { Forward, Reverse }

/// 规划 → 控制 的唯一契约
pub struct Trajectory {
    pub header: Header,
    pub points: Vec<TrajPoint>,     // t, x, y, yaw, v, a, kappa, 期望铰接角(倒车)
    pub direction: Direction,
    pub behavior: BehaviorKind,     // 当前行为状态，调试用
}

#[repr(C)]
pub struct ControlCommand {
    pub header: Header,
    pub steer: f32,                 // [-1, 1]
    pub throttle: f32,              // [0, 1]
    pub brake: f32,                 // [0, 1]
    pub retarder: u8,
    pub buttons: Buttons,           // 位标志：转向灯、灯光、雨刷、喇叭、交互键…
}

## 16. 路线图（按退出条件推进，不按日期）

| 阶段 | 内容 | 退出条件 |
|---|---|---|
| **P0 基础设施** | 自研桥接 DLL（遥测 + 输入）；装好 ETS2LA 扩展状态和帧捕获 DLL；GameAdapter、Bus、录制器、Rerun 可视化；相机状态 + 游戏内 AR 叠加；脚本能控制转向；安全监督 v0（看门狗、接管热键） | 录制 1 小时人类驾驶并完整回放；交通车框在车内、车外视角下都能准确叠加；脚本控制转向能闭环跟随固定曲率 |
| **P1 高速 L1** | 地图导出 + 车道图 + 地图匹配；系统辨识；横向 Pure Pursuit → MPC；用特权交通做 ACC；限速 | 高速连续 100 km 无接管，车道中心偏差 < 0.3 m |
| **P2 高速 L2** | 路线跟随、变道、汇入/驶出、收费站；预测 v1；Frenet 规划 | 跨城高速段全程无接管，0 违章罚单 |
| **P3 全路网 L3** | 信号灯、让行、环岛、城市转弯（挂车包络优化）；场景化行为层；离线闭环仿真上线 | 城市到城市、门到场站门口，每百公里违章 < 1 |
| **P4 门到门 L4** | 场站倒车入位（Hybrid A* + 倒车 MPC） | 困难泊车成功率 ≥ 90% |
| **P5 学习化** | 自动标注 → 视觉栈；学习型预测和规划器（影子模式对比后上线）；纯视觉降级模式 | 关掉特权交通数据仍能高速 L2（车内视角），车外视角下按 §6.7 降级运行；学习规划器在场景库上全面优于规则规划器 |
| **P6 全职业 L5** | 接单、加油、休息、轮渡/火车的 UI 自动化；夜间和雨天鲁棒性；端到端蒸馏模型 | 连续游戏内一周无人干预完成多单交付 |

P0 阶段做好录制，之后的每次驾驶（包括人类驾驶）都会成为训练和测试数据。所以录制器要在第一阶段就写好，越早开始积累越划算。

## 17. 风险与对策

| 风险 | 对策 |
|---|---|
| 游戏更新导致内存读取插件失效 | Steam 测试版锁定版本；插件启动版本校验；特权与视觉双源交叉校验，失效时自动降级 |
| 地图格式随版本变化 | 依赖持续维护的 TruckLib；导出结果按版本 + mod 哈希缓存；投影叠加自检 |
| 8GB 显存与游戏争抢 | 推理预算 ≤ 2GB，TensorRT 量化；必要时第二 GPU 或远程推理 |
| 车外视角前方被自己的挂车遮挡 | 驾驶主回路不依赖画面；视觉能力按视角分级，并用后视镜做盲区检测；必要时提示或自动切回车内视角 |
| 挂车倒车不稳定 | 铰接角闭环 + 折叠约束；先在离线仿真中验证 |
| 学习模型行为不可控 | 学习模型只出候选，规则层校验否决；独立安全监督；影子模式上线 |
| 许可证（GPL 组件、AGPL 检测框架） | 自用无碍；运行时终态只依赖 MIT 组件，GPL v2 的 TruckLib 只在独立的离线导出器里；检测模型选 Apache-2.0 许可的 |
| Rust DLL 在游戏进程内 panic 导致游戏崩溃 | FFI 入口全部 `catch_unwind`；DLL 只做采集转发；重逻辑都在外部进程 |
| 联机环境违规 | 只在单机模式运行 |
